\section*{Part I: Executive Summary}

\subsection*{The Problem}
Commercial kitchens need to stay clean, safe, and pest-free. A camera-based pest detector could help by monitoring kitchens during off hours and alerting staff when rats, mice, or cockroaches appear. The main obstacle is data. Real pest footage from kitchens is hard to collect, rare when things are going well, and expensive to label frame by frame.

Our project studies whether synthetic data can help solve this problem. Instead of waiting for large amounts of real footage, we generate our own labeled pest scenes automatically. This lets us create training examples for all three target pests while controlling where the pest appears, how large it is, and whether the frame contains a pest at all.

\subsection*{Method}
Our method is a synthetic video-data pipeline built around Blender. We first collect kitchen background images and curate three-dimensional pest models for rats, mice, and cockroaches. We then generate short synthetic clips by placing a pest into a kitchen scene, rendering each frame, and exporting a bounding box automatically from the rendered geometry. This avoids manual labeling and lets us control class balance, object scale, motion, and empty frames.

Because our training code expects a standard object-detection dataset, we flatten the rendered clips into labeled frames and split them into training, validation, and test sets. We then train and evaluate detection models on those frames. In practice, we implemented both a transformer-style detector (DETR) and a more conventional detector (Faster R-CNN), then compared how they behaved on the same synthetic benchmark.

The system now supports:
\begin{itemize}[leftmargin=1.5em]
    \item three pest classes: rat, mouse, and cockroach,
    \item 30-second synthetic clips,
    \item frames with pests and frames with no pests,
    \item automatic train/validation/test splitting,
    \item detector training and evaluation,
    \item demo video export and diagnostic visualizations.
\end{itemize}

\subsection*{Results}
The project reached an important milestone: the full local synthetic pipeline now works end to end. We can generate clips, export labels, train a detector, evaluate it, and inspect the predictions visually.

We tested two detector families. We first implemented DETR, a transformer-based detector, because the assignment specifically points toward vision transformers. DETR trained successfully, but on our current smoke-scale synthetic benchmark it did not produce a reliable operating point. Its confidence scores collapsed, meaning it could not clearly separate positive frames from negative frames.

We then trained a Faster R-CNN baseline on the same data. This model performed much better on the current held-out synthetic benchmark. On our latest local dataset, called \texttt{video\_frame\_smoke\_v5}, Faster R-CNN achieved:
\begin{itemize}[leftmargin=1.5em]
    \item recall: 1.0,
    \item precision: 1.0,
    \item frame-level false positive rate: 0.0
\end{itemize}
at confidence thresholds 0.5 and 0.2.

The current benchmark was built from 12 synthetic clips, each 30 seconds long, for a total of 1440 rendered frames. After flattening, we split those frames into 1008 training examples, 216 validation examples, and 216 test examples. The final Faster R-CNN run also remained numerically stable throughout training, with no skipped training or validation batches under the positive-anchor batching strategy.

These numbers are only for the local synthetic held-out split, not for real kitchen footage or instructor-provided test videos. Even so, they show that the data pipeline itself is coherent and that the synthetic data are strong enough to support at least one stable baseline detector.

\subsection*{Why This Matters}
The main contribution of the current stage is not a final production-ready pest detector. It is a working synthetic data pipeline plus a validated local baseline. That is important because it moves the project out of the ``still debugging the pipeline'' stage and into the ``now we can scale, improve realism, and test generalization'' stage.

In practical terms, we now know:
\begin{itemize}[leftmargin=1.5em]
    \item automated synthetic pest clip generation is feasible,
    \item per-frame bounding-box labeling works,
    \item negative examples can be included without breaking training,
    \item model choice matters a lot under this synthetic setup.
\end{itemize}

\subsection*{Current Limitations}
Although the local baseline is strong, the project is not finished. The current system still has several important limitations:
\begin{itemize}[leftmargin=1.5em]
    \item it has only been validated at smoke scale, not at full assignment scale,
    \item it does not yet adapt scene layout from a single user-provided kitchen image,
    \item the strongest current model is Faster R-CNN rather than the transformer-based model we initially hoped to use,
    \item the reported results are synthetic held-out results, not real-world kitchen results.
\end{itemize}

\subsection*{Future Work}
The next step is to push from a local smoke-scale baseline to an assignment-scale pipeline. That means generating more and longer clips, moving closer to 30--60 second production-style runs, and validating the system on harder external test data. We also want to revisit transformer-based detection once the larger video pipeline is in place, because the assignment still motivates that direction. Finally, we need to add scene adaptation from a single kitchen image so that the generated videos better match the target environment.

\section*{Part II: FAQ}

\subsection*{1. Why not just use real pest footage?}
In an ideal world, we would. The problem is that high-quality real pest footage from kitchens is hard to collect, rare when kitchens are well managed, and time-consuming to label. Synthetic data gives us a way to start building and testing the system without waiting for a large real dataset.

\subsection*{2. What exactly is synthetic about the data?}
The scenes are rendered automatically. We take kitchen background images, insert pest models into them, and export the labels directly from the rendered geometry. That means the images are artificial, but the labels are exact by construction.

\subsection*{3. What pests does the current system support?}
The current repository supports three classes:
\begin{itemize}[leftmargin=1.5em]
    \item rat,
    \item mouse,
    \item cockroach.
\end{itemize}

\subsection*{4. Are you generating images or videos?}
We now generate short synthetic clips and export every frame with labels. In practice, the detector is trained on the frames extracted from those clips. So the current system is video-aware, but the training format is still a flattened frame dataset rather than a temporal video model.

\subsection*{5. Did the transformer-based model work?}
Partially. DETR trained and produced outputs, so the implementation itself worked. But on the current synthetic held-out benchmark, DETR could not find a clean confidence threshold that separated positive frames from negative frames. In other words, the model was trainable but not yet useful as the main baseline.

\subsection*{6. Why did Faster R-CNN work better?}
On the current synthetic benchmark, Faster R-CNN produced much better score separation between positive and negative frames. It also handled the current smoke-scale dataset more robustly. This suggests that the current synthetic regime is easier for a more conventional detector than for DETR.

\subsection*{7. Are the current results ``good enough'' to claim success?}
They are good enough to claim that the local synthetic pipeline works and that one detector baseline performs strongly on the local synthetic held-out split. They are not enough to claim final success on the full assignment, because we still need larger-scale generation, single-image kitchen adaptation, and evaluation on external test videos.

\subsection*{8. Could the model just be memorizing the synthetic style?}
Yes, that is a real concern. A model can perform well on synthetic held-out data and still fail on real video. That is why we are careful to describe the current results as local synthetic smoke-scale results, not final real-world performance.

\subsection*{9. Why are negative frames so important?}
In kitchen monitoring, false alarms matter. A detector that constantly reports pests in empty frames would not be useful in practice. Negative frames teach the detector when \emph{not} to fire, and they make false positive rate a meaningful metric.

\subsection*{10. What is the most important thing the project has accomplished so far?}
The most important accomplishment is that the entire local pipeline now works together: generation, labeling, splitting, training, evaluation, visual diagnosis, and demo artifacts. That gives us a solid base for the final stretch of the project.

\subsection*{11. What remains before the project fully matches the assignment prompt?}
Three items matter most:
\begin{itemize}[leftmargin=1.5em]
    \item scaling from smoke-scale runs to assignment-scale generation,
    \item adapting the synthetic scene from a single kitchen image,
    \item validating performance on harder test videos beyond the synthetic held-out split.
\end{itemize}

\subsection*{12. If a skeptical reader asked whether this project is still worthwhile even without final real-video validation, what would you say?}
Yes. Even before final external validation, the project is worthwhile because it solves the hard engineering problem of building a controllable, labeled synthetic video pipeline for pests in kitchens. That infrastructure is a real result on its own, and it is exactly what makes later model comparison and generalization studies possible.

\section*{Part III: Technical Appendix}

\section{Problem Statement}
We study an object-detection problem in kitchen scenes. Let
\[
x_t \in \mathbb{R}^{H \times W \times 3}, \qquad t=1,\dots,T,
\]
denote the frames of a kitchen video clip. For each frame, the detector must identify whether a pest is present, classify its type, and predict a bounding box. The target class set is
\[
\mathcal{C}=\{\text{rat}, \text{mouse}, \text{cockroach}\}.
\]

For a single frame $x$, the ground-truth annotation is a finite set
\[
y=\{(c_i,b_i)\}_{i=1}^{N_x},
\]
where $N_x$ is the number of pests visible in the frame, $c_i \in \mathcal{C}$ is the class label, and
\[
b_i=(x_{c,i}, y_{c,i}, w_i, h_i)\in[0,1]^4
\]
is the normalized center-width-height box for the $i$th pest.

We write the detector as
\[
f_\theta : \mathbb{R}^{H \times W \times 3} \to \widehat{\mathcal{Y}},
\]
where $\theta$ are model parameters and $\widehat{\mathcal{Y}}$ is the space of predicted labeled boxes. Given a training dataset
\[
\mathcal{D}=\{(x^{(m)}, y^{(m)})\}_{m=1}^{n},
\]
the generic supervised objective is
\[
\hat{\theta}
=
\arg\min_{\theta}
\frac{1}{n}\sum_{m=1}^{n}
\mathcal{L}\bigl(f_\theta(x^{(m)}), y^{(m)}\bigr).
\]

The full assignment target is more ambitious than this framewise formulation. Ideally, the system should take a kitchen photo, adapt a synthetic scene to that layout, generate 30--60 second labeled pest clips, and train a vision-transformer detector that generalizes to external test videos. From a distributional perspective, if $P_{\mathrm{syn}}$ denotes the synthetic frame distribution and $P_{\mathrm{real}}$ the target real-world kitchen distribution, then the key challenge is that
\[
P_{\mathrm{syn}} \neq P_{\mathrm{real}}.
\]

\section{Related Work}
Transformer-based detection is represented here by DETR, which formulates object detection as direct set prediction rather than proposal generation plus postprocessing \cite{carion2020detr}. DETR is relevant because the assignment explicitly points toward a vision-transformer-style detector.

Synthetic data generation is a natural fit for rare-event vision problems because it replaces expensive manual labeling with controllable rendering. The main challenge is domain gap. A synthetic pipeline can provide clean labels and broad scene variation, but the resulting model may still overfit to rendered textures, object placement patterns, or lighting statistics.

Our contribution is therefore primarily systems and empirical rather than architectural. We build a reproducible pipeline for kitchen-background collection, Blender-based pest clip generation, per-frame labeling, detector training, and diagnosis, then study what detector behavior looks like under that pipeline.

\section{Method}
\subsection{Pipeline Overview}
The repository implements the following automated workflow:
\begin{enumerate}[leftmargin=1.5em]
    \item collect kitchen background images,
    \item organize pest assets by class,
    \item generate synthetic clips with per-frame labels,
    \item flatten frames into a standard detection dataset,
    \item split the dataset into train/validation/test partitions,
    \item train and evaluate detectors,
    \item generate diagnostics, overlays, demo videos, and report figures.
\end{enumerate}

\subsection{Background Collection and Assets}
Kitchen backgrounds are collected from Places365 and filtered to kitchen-related scene categories such as \texttt{kitchen} and \texttt{restaurant\_kitchen}. Pest assets are organized under:
\begin{itemize}[leftmargin=1.5em]
    \item \texttt{assets/models/rat/},
    \item \texttt{assets/models/mouse/},
    \item \texttt{assets/models/cockroach/}.
\end{itemize}

The project includes an asset audit stage because not every downloaded model rendered plausibly. The current smoke-scale video runs use curated model pools and explicit exclude lists.

\subsection{Synthetic Video Generation}
The core generator is Blender-based and operates clip by clip. For each clip, a background
\[
B \sim P_B,
\]
a pest asset
\[
A \sim P_A,
\]
and a set of nuisance parameters
\[
\phi \sim P_{\Phi}
\]
are sampled. Here $\phi$ includes position, scale, heading, class-dependent motion, pauses, negative-frame injection, and visibility filtering. For a clip of length $T$, the generator produces
\[
x_t = G(B, A, \phi_t), \qquad t=1,\dots,T,
\]
with labels
\[
y_t = T(A, \phi_t).
\]

The current smoke-scale configuration uses 30-second clips at 4 FPS. The generator also supports:
\begin{itemize}[leftmargin=1.5em]
    \item negative clips with no pest,
    \item negative frames inside positive clips,
    \item shard-friendly clip indexing via \texttt{start\_clip},
    \item curated model directories plus exclude lists,
    \item visibility filtering so that tiny or nearly invisible positives are not mislabeled.
\end{itemize}

The concrete scene specification used by the current video generator is fixed enough that another reader could reimplement it directly. Each clip is rendered at resolution $1280 \times 720$ with Blender Cycles. The camera is placed at $(0.0, -3.8, 1.3)$ with Euler rotation $(75^\circ, 0^\circ, 0^\circ)$, the key area light is placed at $(1.5, -2.0, 3.0)$ with energy 1200, and a large emissive background plane is attached to the camera so that a sampled kitchen image fills the view. Pest models are imported from \texttt{.glb}, \texttt{.gltf}, \texttt{.fbx}, or \texttt{.obj}, recentered so that their combined mesh bounding box is centered at the origin and grounded to the floor plane, then pose-adjusted by class. In particular, the rat asset is rotated by $(0^\circ, 90^\circ, 0^\circ)$ so that it lies on the floor correctly under the current scene convention.

The generator samples class-dependent scale and motion parameters. Let $s$ denote the target normalized model size before box-based correction and let $a$ denote the desired normalized bbox area. Then:
\begin{itemize}[leftmargin=1.5em]
    \item rat: $s \sim \mathrm{Unif}(0.12, 0.22)$, $a \sim \mathrm{Unif}(0.0060, 0.0200)$, speed $\sim \mathrm{Unif}(0.006, 0.012)$,
    \item mouse: $s \sim \mathrm{Unif}(0.10, 0.18)$, $a \sim \mathrm{Unif}(0.0040, 0.0150)$, speed $\sim \mathrm{Unif}(0.009, 0.016)$,
    \item cockroach: $s \sim \mathrm{Unif}(0.08, 0.14)$, $a \sim \mathrm{Unif}(0.0030, 0.0120)$, speed $\sim \mathrm{Unif}(0.012, 0.020)$.
\end{itemize}
An initial state is sampled by drawing a location $(x,y)$ uniformly from $[-0.9,0.9] \times [-0.4,0.8]$, drawing a heading uniformly from $[0,2\pi)$, checking visibility in camera coordinates, and then rescaling the model so that the projected box area lands inside the class-specific target interval. If no valid state is found after 50 attempts, the clip generation fails rather than silently producing a bad example.

Motion is first-order and class-aware. At each frame, the heading receives a perturbation from $\mathrm{Unif}(-0.12,0.12)$ radians. With probability \texttt{pause\_prob}, the current speed is multiplied by a factor from $\mathrm{Unif}(0.15, 0.55)$; otherwise it is multiplied by a factor from $\mathrm{Unif}(0.96, 1.04)$. The updated speed is clipped back to the class-specific speed range. Position is then advanced by $(\cos \theta \cdot v, \sin \theta \cdot v)$ and reflected off the rectangular motion bounds $x \in [-0.95,0.95]$, $y \in [-0.45,0.85]$ by a bounce rule that flips heading about the corresponding axis.

Negative examples are injected in two ways. First, each clip is made fully negative with probability \texttt{negative\_clip\_prob}. Second, conditional on being a positive clip, exactly
\[
\operatorname{round}(T \cdot p_{\mathrm{negframe}})
\]
frame indices are sampled uniformly without replacement and rendered as negative frames with the pest hidden. A projected bounding box is accepted only if at least $\max(6, 0.08V)$ mesh vertices are visible in the camera view, where $V$ is the total number of mesh vertices considered, and only if the final normalized box area is at least \texttt{min\_bbox\_area}. Otherwise that frame is converted to a negative frame and counted as visibility-filtered.

\subsection{Label Format}
Bounding boxes are exported in normalized center-width-height form. For a pixel-space box
\[
(x_{\min}, y_{\min}, x_{\max}, y_{\max}),
\]
we define
\[
x_c=\frac{x_{\min}+x_{\max}}{2}, \qquad
y_c=\frac{y_{\min}+y_{\max}}{2}, \qquad
w=x_{\max}-x_{\min}, \qquad
h=y_{\max}-y_{\min}.
\]
If the image size is $W \times H$, then the normalized box is
\[
\tilde{b}
=
\left(
\frac{x_c}{W},
\frac{y_c}{H},
\frac{w}{W},
\frac{h}{H}
\right)\in[0,1]^4.
\]
Each annotation therefore has the form
\[
y=(c,\tilde{b}),
\]
where $c \in \{\text{rat}, \text{mouse}, \text{cockroach}\}$.

\subsection{Video-to-Detection Reuse}
The current detector stack consumes an image-detection dataset rather than a temporal model input. We therefore flatten clip folders into:
\begin{itemize}[leftmargin=1.5em]
    \item \texttt{images/},
    \item \texttt{labels/},
    \item \texttt{manifest.csv}.
\end{itemize}
This allows reuse of the same splitting, training, and evaluation code on video-derived frames.

\subsection{Detectors}
We implemented DETR as the initial transformer-based detector \cite{carion2020detr}. DETR predicts a fixed set of slots
\[
\hat{y}_i=(\hat{p}_i,\hat{b}_i), \qquad i=1,\dots,Q,
\]
where $\hat{p}_i$ is a class distribution over the pest classes plus a no-object class and $\hat{b}_i \in [0,1]^4$ is a normalized box. Training uses Hungarian matching to align predictions and ground-truth objects.

We also implemented a torchvision Faster R-CNN baseline. This became the practical local baseline after diagnosis because DETR exhibited confidence and ranking collapse on the current synthetic video-frame split, while Faster R-CNN trained cleanly and separated positive from negative frames much more reliably. We stabilized Faster R-CNN further with a \texttt{positive\_anchor} batching strategy, which ensures that each mini-batch contains at least one positive frame and avoids all-negative mini-batches that can cause non-finite losses in heavily negative datasets.

This matters because naive batching with batch size 2 would naturally create many all-negative mini-batches.

\subsection{Training Protocol}
The DETR runs in this repository were primarily smoke and diagnostic experiments. The current stable local baseline uses Faster R-CNN with:
\begin{itemize}[leftmargin=1.5em]
    \item architecture: \texttt{fasterrcnn\_mobilenet\_v3\_large\_320\_fpn},
    \item pretrained torchvision weights,
    \item 3 epochs,
    \item batch size 2,
    \item learning rate $5 \times 10^{-5}$,
    \item gradient clipping norm 5.0,
    \item \texttt{positive\_anchor} batching,
    \item zero worker subprocesses on Windows for stability.
\end{itemize}

More explicitly, the detector is the torchvision implementation of Faster R-CNN with a MobileNetV3-Large-320-FPN backbone initialized from default pretrained torchvision detection weights, followed by replacement of the ROI classification head so that the final predictor has four output classes: background plus the three pest classes. The class-to-index mapping is
\[
0 \mapsto \text{rat}, \qquad 1 \mapsto \text{mouse}, \qquad 2 \mapsto \text{cockroach},
\]
and torchvision internally shifts these to labels $\{1,2,3\}$ because label 0 is reserved for background.

Each training image is loaded as RGB, converted to a tensor, and paired with a target dictionary containing \texttt{boxes}, \texttt{labels}, \texttt{image\_id}, \texttt{area}, and \texttt{iscrowd}. Labels stored on disk in normalized center-width-height format are converted back to pixel-space \texttt{xyxy} boxes before training. Optimization uses AdamW with learning rate $5 \times 10^{-5}$ and weight decay $10^{-4}$. The code trains for 3 epochs, computes the mean finite training loss per epoch, computes validation loss by running the detector in loss-producing mode on the validation loader, writes a \texttt{last} checkpoint every epoch, and writes a \texttt{best} checkpoint whenever validation loss improves. The final reported v5 baseline is selected from that \texttt{best} checkpoint.

The \texttt{positive\_anchor} batching strategy is part of the reproducible method rather than an incidental implementation trick. Let $P$ be the set of indices with at least one ground-truth box and $N$ the set of empty-frame indices. For batch size 2, the sampler forms each batch by first choosing one anchor from $P$ and then filling the remaining slot from a shuffled pool consisting of all negatives plus extra positives. This guarantees at least one positive image per batch whenever positive images exist, which is why the v5 run avoids the non-finite all-negative batch behavior seen under naive batching on a roughly 54\% negative-frame dataset.

\subsection{Evaluation Protocol}
The current evaluation pipeline is thresholded rather than mAP-based. A predicted labeled box $(\hat{c}, \hat{b})$ is counted as a true positive when:
\begin{enumerate}[leftmargin=1.5em]
    \item the predicted class matches the ground-truth class,
    \item the confidence exceeds a chosen threshold $\tau_{\mathrm{conf}}$,
    \item the box overlap satisfies
    \[
    \operatorname{IoU}(\hat{b}, b)\ge \tau_{\mathrm{IoU}}.
    \]
\end{enumerate}

We compute
\[
\operatorname{Precision}=\frac{TP}{TP+FP},
\qquad
\operatorname{Recall}=\frac{TP}{TP+FN},
\qquad
\operatorname{TDR}=\operatorname{Recall}.
\]

The current false positive metric is frame-level on negative frames:
\[
\operatorname{FPR}_{\mathrm{frame}}
=
\frac{\#\{\text{negative frames with at least one prediction}\}}
{\#\{\text{negative frames}\}}.
\]
The main reported operating points are confidence thresholds 0.5 and 0.2 with IoU threshold 0.5.

\subsection{DETR Diagnosis}
The DETR diagnosis is informative. Its held-out v4 test recall is zero at thresholds 0.5 and 0.2, but this is not because it produces no scores at all. Diagnostics show that:
\begin{itemize}[leftmargin=1.5em]
    \item top scores on positive and negative frames cluster around 0.025,
    \item thresholds of 0.05 and above suppress all predictions,
    \item even top-$k$ truncation does not recover a clean operating point,
    \item at threshold 0.01, recall rises but frame FPR reaches 1.0.
\end{itemize}
This is best interpreted as confidence and ranking collapse.

\subsection{Faster R-CNN Diagnosis}
The Faster R-CNN diagnostics show healthy score separation:
\begin{itemize}[leftmargin=1.5em]
    \item on v5 test frames, positive top-score quantiles are high,
    \item negative-frame top scores are exactly 0.0,
    \item thresholds 0.5 and 0.2 both remain clean,
    \item positive-anchor batching eliminates skipped train/validation batches.
\end{itemize}

\subsection{Exact Data Contract}
The current reproducible pipeline assumes the following on-disk contracts.

Kitchen backgrounds live under a directory such as \texttt{data/raw/kitchen\_backgrounds/} and may be nested arbitrarily; all \texttt{.jpg}, \texttt{.jpeg}, and \texttt{.png} files are considered eligible backgrounds. Pest assets are grouped by class under model directories and may be in \texttt{.glb}, \texttt{.gltf}, \texttt{.fbx}, or \texttt{.obj} format. The raw video generator writes one directory per clip:
\begin{itemize}[leftmargin=1.5em]
    \item \texttt{clips/<clip\_id>/frames/frame\_<k>.png},
    \item \texttt{clips/<clip\_id>/labels/frame\_<k>.txt},
    \item \texttt{clips/<clip\_id>/clip\_metadata.json}.
\end{itemize}
Each label file is either empty, meaning no pest is present in that frame, or contains one line of the form
\[
\texttt{class\_id xc yc w h}
\]
with all four box coordinates normalized to $[0,1]$. The class IDs are 0 for rat, 1 for mouse, and 2 for cockroach.

Flattening rewrites this clip-structured data into an image-detection layout:
\begin{itemize}[leftmargin=1.5em]
    \item \texttt{images/<clip\_id>\_frame\_<k>.png},
    \item \texttt{labels/<clip\_id>\_frame\_<k>.txt},
    \item \texttt{manifest.csv}.
\end{itemize}
The split script then writes \texttt{split.json} containing absolute \texttt{data\_dir}, integer \texttt{seed}, and three stem lists named \texttt{train}, \texttt{val}, and \texttt{test}. Stratification is performed by the first label ID in each label file, with empty files treated as class $-1$. In other words, negatives are stratified separately from rat, mouse, and cockroach frames.

\subsection{Step-by-Step Reproduction Recipe}
The current main local benchmark can be reproduced in five deterministic stages.

\paragraph{Stage 1: Generate synthetic clips.}
Run Blender in background mode with the video generator, supplying kitchen backgrounds, curated pest model directories, and the smoke-scale hyperparameters. The exact v5-style configuration is:
\begin{itemize}[leftmargin=1.5em]
    \item \texttt{num\_clips = 12},
    \item \texttt{duration\_seconds = 30},
    \item \texttt{fps = 4}, so $T = 120$ frames per clip,
    \item \texttt{samples = 32},
    \item \texttt{width = 1280}, \texttt{height = 720},
    \item \texttt{min\_bbox\_area = 0.01},
    \item \texttt{negative\_clip\_prob = 0.15},
    \item \texttt{negative\_frame\_prob = 0.10},
    \item \texttt{pause\_prob = 0.10},
    \item \texttt{seed = 42},
    \item per-clip RNG seed \texttt{clip\_seed = seed + clip\_number}.
\end{itemize}
If a strict class balance is desired, the reader should additionally pass a repeated \texttt{clip\_class\_sequence} such as rat, mouse, cockroach, rat, mouse, cockroach, and so on; otherwise class identity is sampled uniformly from the available model pools on each non-negative clip.

\paragraph{Stage 2: Flatten clip frames into a detection dataset.}
Copy or symlink every rendered frame-label pair into \texttt{images/} and \texttt{labels/} using a flattened stem of the form \texttt{clip\_000123\_frame\_000045}. The repository default is \texttt{copy} mode.

\paragraph{Stage 3: Build the split.}
Apply the split script with train, validation, and test ratios 0.7, 0.15, and 0.15 and seed 42. Because splitting is stratified by first label ID, the negative-frame rate is preserved approximately across splits. For the current reported v5 benchmark, this produced 1008 train frames, 216 validation frames, and 216 test frames from 1440 total rendered frames.

\paragraph{Stage 4: Train Faster R-CNN.}
Train the torchvision Faster R-CNN baseline with
\begin{itemize}[leftmargin=1.5em]
    \item \texttt{arch = fasterrcnn\_mobilenet\_v3\_large\_320\_fpn},
    \item \texttt{weights = default},
    \item \texttt{epochs = 3},
    \item \texttt{batch\_size = 2},
    \item \texttt{lr = 5e-5},
    \item \texttt{weight\_decay = 1e-4},
    \item \texttt{grad\_clip\_norm = 5.0},
    \item \texttt{batching\_strategy = positive\_anchor},
    \item \texttt{num\_workers = 0},
    \item \texttt{seed = 42}.
\end{itemize}
The run should emit \texttt{model.pt} and \texttt{metadata.json} under both \texttt{last/} and \texttt{best/}, plus a top-level \texttt{train.log} and \texttt{summary.json}. The reported appendix numbers correspond to evaluating \texttt{best/model.pt}, not the last epoch unconditionally.

\paragraph{Stage 5: Evaluate the held-out test split.}
Evaluate \texttt{best/model.pt} at confidence thresholds 0.5 and 0.2 with IoU threshold 0.5. The evaluation loop sorts predictions by score, greedily matches them to unused same-class ground-truth boxes, and then reports TP, FP, FN, recall, precision, negative-frame count, false-positive count on negative frames, and frame-level FPR. For the current reported local smoke-scale v5 benchmark, the held-out test split result is recall 1.0, precision 1.0, and frame-level FPR 0.0 at both thresholds 0.5 and 0.2.

\section{Discussion}
\subsection{Why the Current Results Matter}
The current results show that:
\begin{enumerate}[leftmargin=1.5em]
    \item the synthetic clip generator can produce coherent labeled data,
    \item the flattened frame pipeline can train a detector reproducibly,
    \item negative examples can be incorporated without destabilizing the current Faster R-CNN baseline,
    \item model architecture choice matters strongly in this regime.
\end{enumerate}

\subsection{Limitations}
The current system still has several important limitations.

First, the strongest baseline is not the transformer-based model originally hoped for. Second, the results are purely local synthetic held-out results and do not prove real-world or instructor-test generalization. Third, the generator is still smoke-scale rather than assignment-scale. Fourth, the repository still does not adapt scene layout from a single user-provided kitchen image.

\subsection{Expected Failure Modes Beyond the Current Split}
Even though v5 performs perfectly on the local synthetic held-out split, several failure modes are still likely in harder settings:
\begin{itemize}[leftmargin=1.5em]
    \item domain shift from rendered kitchen backgrounds to real camera footage,
    \item missed detections under stronger occlusion or clutter,
    \item sensitivity to unseen pest shapes or asset textures,
    \item failure under layout conditions not represented in the current background pool,
    \item degraded performance when clip duration, motion, or scene complexity scale up.
\end{itemize}

\section{Future Work}
The next development steps are:
\begin{enumerate}[leftmargin=1.5em]
    \item scale the generator from smoke-scale 30-second runs to assignment-scale 30--60 second batches,
    \item add scene adaptation from a single user-provided kitchen image or justify a baseline approximation,
    \item validate the current baseline on external or instructor-provided test videos,
    \item revisit transformer-based detectors after the larger video pipeline is in place,
    \item expand model diversity, hard negatives, and realism to reduce synthetic-to-real domain gap,
    \item study whether synthetic pretraining plus limited real fine-tuning improves robustness.
\end{enumerate}

\section{Conclusion}
This project develops a reproducible synthetic-data pipeline for pest detection in kitchen environments. The repository now goes beyond static image generation: it supports smoke-scale 30-second clip generation, per-frame label export, video-to-detection flattening, detector training, diagnostics, demo video assembly, and report-ready artifacts.

Empirically, the strongest current local baseline is Faster R-CNN with positive-anchor batching on \texttt{video\_frame\_smoke\_v5}. On the local held-out synthetic test split, this model achieves recall 1.0, precision 1.0, and frame-level false positive rate 0.0 at confidence thresholds 0.5 and 0.2. DETR, while implemented successfully, currently suffers from confidence and ranking collapse on the analogous smoke-scale video-frame split and is therefore not the recommended local baseline at this stage.

The main contribution of the current project stage is therefore twofold: a working synthetic video-frame generation and labeling pipeline, and a stable local detector baseline that demonstrates the pipeline can support meaningful training and evaluation. The major remaining gap is not basic engineering feasibility. It is closing the distance from local synthetic smoke-scale success to assignment-scale video generation, single-image scene adaptation, and external validation on held-out test videos.
