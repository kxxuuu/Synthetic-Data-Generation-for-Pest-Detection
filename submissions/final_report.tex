\section*{Part I: Executive Summary}

\subsection*{The Problem}
Commercial kitchens need to stay clean, safe, and pest-free. A camera-based pest detector could help by monitoring kitchens during off hours and alerting staff when rats, mice, or cockroaches appear. The main obstacle is data. Real pest footage from kitchens is hard to collect, rare when things are going well, and expensive to label frame by frame.

Our project studies whether synthetic data can help solve this problem. Instead of waiting for large amounts of real footage, we generate our own labeled pest scenes automatically. This lets us create training examples for all three target pests while controlling where the pest appears, how large it is, and whether the frame contains a pest at all.

\subsection*{Our Approach}
Our approach follows a staged synthetic-data detection pipeline. We first collected kitchen background imagery and curated pest assets for the three target classes: rat, mouse, and cockroach. We then used a Blender-based generation framework to render labeled synthetic clips, with automatic frame-level bounding-box export. After generation, we transformed the clips into a standard object-detection dataset by flattening frames, exporting labels, and creating train, validation, and test splits.

On top of this dataset pipeline, we trained and compared two detector frameworks. The first was DETR, which served as the transformer-based detection baseline. The second was Faster R-CNN, which served as a region-based comparison baseline. We then evaluated both models on held-out synthetic video-frame data and used diagnostic analyses to study detection quality, score behavior, and false-positive performance.


\subsection*{Results}
The project reached an important milestone: the full local synthetic pipeline now works end to end. We can generate clips, export labels, train a detector, evaluate it, and inspect the predictions visually.

We tested two detector families. The transformer-based model trained successfully, but on our current smoke-scale benchmark it did not separate pest frames from empty frames reliably. A more conventional detector worked much better on the same data.

Our current best benchmark contains 12 synthetic clips, each 30 seconds long, for a total of 1440 rendered frames. After splitting those frames into training, validation, and test sets, the strongest detector achieved: recall: 1.0, precision: 1.0, frame-level false positive rate: 0.0, on the local held-out synthetic test split. These numbers are not final real-world results, but they do show that the data pipeline itself is coherent and that the synthetic data are strong enough to support at least one stable baseline detector. Intuitively, the transformer-based detector appears to need a larger and more mature training setup than we currently have. On our present synthetic benchmark, it did not learn a reliable way to distinguish pest frames from empty frames, so it either missed almost everything or became too trigger-happy when we relaxed the decision rule. Faster R-CNN fit this stage of the project better. The current dataset is still relatively small, highly controlled, and contains many empty frames, and the more conventional detector handled that setting much more robustly. For that reason, we still include DETR as an important transformer-direction experiment, but we report Faster R-CNN as the strongest current local baseline rather than claiming that the transformer approach is already ready for final use.

\subsection*{Why This Matters}
The main contribution at the current stage is not yet a final production-ready pest detector, but rather a working synthetic data pipeline together with a validated local baseline. This matters because the project has clearly moved beyond the ``still debugging the pipeline'' stage and into a more meaningful phase where scaling, realism improvements, and generalization testing can be pursued on top of a functioning system. In practical terms, the current results show that automated synthetic pest clip generation is feasible, per-frame bounding-box labeling works reliably, negative examples can be incorporated without breaking training, and model choice matters substantially under this synthetic setup.

\subsection*{Current Limitations}
Although the local baseline is strong, the project is not finished. The current system still has several important limitations. It has only been validated at smoke scale rather than at full assignment scale, it does not yet adapt scene layout from a single user-provided kitchen image, the strongest current model is still the more conventional detector rather than the transformer-based model we initially hoped to use, and the reported results remain synthetic held-out results rather than real-world kitchen results.

\subsection*{Future Work}
The next step is to push from a local smoke-scale baseline to an assignment-scale pipeline. That means generating more and longer clips, moving closer to 30--60 second production-style runs, and validating the system on harder external test data. We also want to revisit transformer-based detection once the larger video pipeline is in place, because the assignment still motivates that direction. Finally, we need to add scene adaptation from a single kitchen image so that the generated videos better match the target environment.

\section*{Part II: FAQ}

\subsection*{1. Why not just use real pest footage?}
In an ideal world, we would. The problem is that high-quality real pest footage from kitchens is hard to collect, rare when kitchens are well managed, and time-consuming to label. Synthetic data gives us a way to start building and testing the system without waiting for a large real dataset.

\subsection*{2. What exactly is synthetic about the data?}
The scenes are rendered automatically. We take kitchen background images, insert pest models into them, and export the labels directly from the rendered geometry. That means the images are artificial, but the labels are exact by construction.

\subsection*{3. What pests does the current system support?}
The current repository supports three classes: rat, mouse, cockroach.

\subsection*{4. Are you generating images or videos?}
We now generate short synthetic clips and export every frame with labels. In practice, the detector is trained on the frames extracted from those clips. So the current system is video-aware, but the training format is still a flattened frame dataset rather than a temporal video model.

\subsection*{5. Did the transformer-based model work?}
Partially. DETR trained and produced outputs, so the implementation itself worked. But on the current synthetic held-out benchmark, DETR could not find a clean confidence threshold that separated positive frames from negative frames. In other words, the model was trainable but not yet useful as the main baseline.

\subsection*{6. Why did Faster R-CNN work better?}
On the current synthetic benchmark, Faster R-CNN produced much better score separation between positive and negative frames. It also handled the current smoke-scale dataset more robustly. This suggests that the current synthetic regime is easier for a more conventional detector than for DETR.

\subsection*{7. Are the current results ``good enough'' to claim success?}
They are good enough to claim that the local synthetic pipeline works and that one detector baseline performs strongly on the local synthetic held-out split. They are not enough to claim final success on the full assignment, because we still need larger-scale generation, single-image kitchen adaptation, and evaluation on external test videos.

\subsection*{8. Could the model just be memorizing the synthetic style?}
Yes, that is a real concern. A model can perform well on synthetic held-out data and still fail on real video. That is why we are careful to describe the current results as local synthetic smoke-scale results, not final real-world performance.

\subsection*{9. Why are negative frames so important?}
In kitchen monitoring, false alarms matter. A detector that constantly reports pests in empty frames would not be useful in practice. Negative frames teach the detector when \emph{not} to fire, and they make false positive rate a meaningful metric.

\subsection*{10. What is the most important thing the project has accomplished so far?}
The most important accomplishment is that the entire local pipeline now works together: generation, labeling, splitting, training, evaluation, visual diagnosis, and demo artifacts. That gives us a solid base for the final stretch of the project.

\subsection*{11. What remains before the project fully matches the assignment prompt?}
Three items matter most:
\begin{itemize}[leftmargin=1.5em]
    \item scaling from smoke-scale runs to assignment-scale generation,
    \item adapting the synthetic scene from a single kitchen image,
    \item validating performance on harder test videos beyond the synthetic held-out split.
\end{itemize}

\subsection*{12. If a skeptical reader asked whether this project is still worthwhile even without final real-video validation, what would you say?}
Yes. Even before final external validation, the project is worthwhile because it solves the hard engineering problem of building a controllable, labeled synthetic video pipeline for pests in kitchens. That infrastructure is a real result on its own, and it is exactly what makes later model comparison and generalization studies possible.

\subsection*{13. Why use video clips if the model is trained on frames?}
Short clips make the synthetic generation process more realistic. They let us vary pose, scale, motion, and occlusion over time instead of rendering isolated still images. Even though training currently uses flattened frames, clip-based generation gives us a better approximation of the kinds of visual changes that appear in real kitchen monitoring footage.

\subsection*{14. Does the current system model realistic pest behavior?}
Only in a limited sense. The current pipeline adds motion and placement variation, but it does not yet simulate full biological behavior or complex interaction with the environment. The goal right now is not perfect behavioral realism, but controllable visual diversity that is sufficient for detector training and debugging.

\subsection*{15. How are the labels generated?}
The labels are exported directly from the rendering process. Because the system knows exactly where each pest model is placed in each frame, it can write bounding boxes automatically without manual annotation. This is one of the main advantages of synthetic data: label generation is fast, consistent, and exact within the rendered scene.

\subsection*{16. Why is exact labeling important?}
Exact labels remove human annotation noise from the training set. That makes it easier to diagnose whether model errors come from the detector itself or from the data pipeline. In early-stage system development, this kind of clean supervision is especially useful because it reduces one major source of uncertainty.

\subsection*{17. What makes this different from a standard object detection project?}
The project is not only about training a detector. A large part of the work is building the synthetic data pipeline itself: scene creation, pest insertion, automatic labeling, dataset splitting, evaluation, and visualization. In that sense, the project is as much a data-generation and experimental infrastructure project as it is a modeling project.

\subsection*{18. Why not train directly on real kitchen images collected from the internet?}
Internet images usually do not match the target setting well. They often have different camera angles, lighting, backgrounds, and image quality from fixed kitchen monitoring footage. They also tend to be weakly labeled or inconsistently labeled. Synthetic generation gives us much more control over the exact environment we want the model to learn from.

\subsection*{19. Is the current dataset large enough?}
It is large enough for smoke-scale experiments and pipeline validation, but not yet large enough to fully support strong claims about final deployment performance. The current dataset is best understood as a controlled benchmark for development, not as the final training corpus for a production-ready detector.

\subsection*{20. What is the role of the held-out synthetic split?}
The held-out synthetic split gives us a clean way to measure whether the model generalizes beyond the exact examples it saw during training. It is still synthetic, so it is not a substitute for real-world testing, but it is an important first check that the model is learning patterns rather than simply memorizing the training set.

\subsection*{21. Why is evaluation on external videos still necessary?}
Because success on synthetic data does not guarantee success on real footage. External videos introduce distribution shifts in texture, lighting, noise, camera perspective, clutter, and pest appearance. Evaluating on those harder videos is the only way to test whether the detector has practical value beyond the synthetic environment.

\subsection*{22. What does ``single-image kitchen adaptation'' mean?}
It means building synthetic scenes from one kitchen image so that the generated examples better match a specific target environment. Instead of using only generic kitchen backgrounds, the pipeline would adapt to the visual style of the actual kitchen where detection is needed. That is important for narrowing the gap between synthetic training data and deployment conditions.

\subsection*{23. Why not use segmentation masks instead of bounding boxes?}
Segmentation could provide richer supervision, but it also increases modeling and evaluation complexity. For the current stage of the project, bounding boxes are the simpler and more standard detection target. They are enough to test whether the synthetic pipeline can support object detection effectively before moving to more detailed annotation formats.

\subsection*{24. Could this pipeline support more pest classes later?}
Yes. The current system supports rat, mouse, and cockroach, but the pipeline is designed so that additional pest classes could be added by introducing new models, placement rules, and label mappings. Expanding the class set is an engineering extension, not a complete redesign of the system.

\subsection*{25. Why are visual diagnosis tools included in the pipeline?}
Visual diagnosis helps verify that the system is working end to end. It lets us inspect generated frames, labels, predictions, and failure cases directly instead of relying only on summary metrics. This is especially important in synthetic-data projects, where silent pipeline mistakes can otherwise go unnoticed.

\subsection*{26. What kinds of failure cases are most important to inspect?}
The most important failure cases are false positives in empty frames, missed detections on small or partially occluded pests, and unstable confidence scores across visually similar frames. These cases tell us whether the detector is robust enough for practical kitchen monitoring rather than just performing well on easy synthetic examples.

\subsection*{27. Does this project replace the need for real data collection?}
No. Synthetic data is a way to accelerate development, not a complete replacement for real data. It helps us build the pipeline, test detector choices, and generate controlled training examples. But real data is still necessary for final validation and for understanding how well the system handles real-world variation.

\subsection*{28. What is the main research value of this project?}
The main research value is showing that a controllable synthetic video pipeline can be built for pest detection in kitchen environments and used to support model training and comparison. That contribution matters even before full real-world validation, because it creates the experimental foundation needed for later generalization studies.

\section*{Part III: Technical Appendix}

\section{Problem Statement}
We study an object-detection problem in kitchen scenes. Let
\[
x_t \in \mathbb{R}^{H \times W \times 3}, \qquad t=1,\dots,T,
\]
denote the frames of a kitchen video clip. For each frame, the detector must identify whether a pest is present, classify its type, and predict a bounding box. The target class set is
\[
\mathcal{C}=\{\text{rat}, \text{mouse}, \text{cockroach}\}.
\]

For a single frame $x$, the ground-truth annotation is a finite set
\[
y=\{(c_i,b_i)\}_{i=1}^{N_x},
\]
where $N_x$ is the number of pests visible in the frame, $c_i \in \mathcal{C}$ is the class label, and
\[
b_i=(x_{c,i}, y_{c,i}, w_i, h_i)\in[0,1]^4
\]
is the normalized center-width-height box for the $i$th pest.

We write the detector as
\[
f_\theta : \mathbb{R}^{H \times W \times 3} \to \widehat{\mathcal{Y}},
\]
where $\theta$ are model parameters and $\widehat{\mathcal{Y}}$ is the space of predicted labeled boxes. Given a training dataset
\[
\mathcal{D}=\{(x^{(m)}, y^{(m)})\}_{m=1}^{n},
\]
the generic supervised objective is
\[
\hat{\theta}
=
\arg\min_{\theta}
\frac{1}{n}\sum_{m=1}^{n}
\mathcal{L}\bigl(f_\theta(x^{(m)}), y^{(m)}\bigr).
\]

The full assignment target is more ambitious than this framewise formulation. Ideally, the system should take a kitchen photo, adapt a synthetic scene to that layout, generate 30--60 second labeled pest clips, and train a vision-transformer detector that generalizes to external test videos. From a distributional perspective, if $P_{\mathrm{syn}}$ denotes the synthetic frame distribution and $P_{\mathrm{real}}$ the target real-world kitchen distribution, then the key challenge is that
\[
P_{\mathrm{syn}} \neq P_{\mathrm{real}}.
\]

\section{Related Work}
Transformer-based detection is represented here by DETR, which formulates object detection as direct set prediction rather than proposal generation plus postprocessing \cite{carion2020detr}. DETR is relevant because the assignment explicitly points toward a vision-transformer-style detector. For a region-based comparison baseline, we also use Faster R-CNN \cite{ren2015fasterrcnn}, which remains a standard two-stage detection framework.

Synthetic data generation is a natural fit for rare-event vision problems because it replaces expensive manual labeling with controllable rendering. The main challenge is domain gap. A synthetic pipeline can provide clean labels and broad scene variation, but the resulting model may still overfit to rendered textures, object placement patterns, or lighting statistics.

Our contribution is therefore primarily systems and empirical rather than architectural. We build a reproducible pipeline for kitchen-background collection, Blender-based pest clip generation, per-frame labeling, detector training, and diagnosis, then study what detector behavior looks like under that pipeline.

\section{Method}
\subsection{Pipeline Overview}
The repository implements an automated workflow that begins with collecting kitchen background images and organizing pest assets by class. It then generates synthetic clips with per-frame labels, flattens the resulting frames into a standard detection dataset, and splits the data into training, validation, and test partitions. Finally, the pipeline trains and evaluates detectors and produces diagnostics, overlays, demo videos, and report figures.


\subsection{Background Collection and Assets}
Kitchen backgrounds are collected from Places365 \cite{zhou2018places} and filtered to kitchen-related scene categories such as \texttt{kitchen} and \texttt{restaurant\_kitchen}. Pest assets are organized under:
\begin{itemize}[leftmargin=1.5em]
    \item \texttt{assets/models/rat/},
    \item \texttt{assets/models/mouse/},
    \item \texttt{assets/models/cockroach/}.
\end{itemize}

The project includes an asset audit stage because not every downloaded model rendered plausibly. The current smoke-scale video runs use curated model pools and explicit exclude lists.

\subsection{Synthetic Video Generation}
The core generator is Blender-based and operates clip by clip. For each clip, a background
\[
B \sim P_B,
\]
a pest asset
\[
A \sim P_A,
\]
and a set of nuisance parameters
\[
\phi \sim P_{\Phi}
\]
are sampled. Here $\phi$ includes position, scale, heading, class-dependent motion, pauses, negative-frame injection, and visibility filtering. For a clip of length $T$, the generator produces
\[
x_t = G(B, A, \phi_t), \qquad t=1,\dots,T,
\]
with labels
\[
y_t = T(A, \phi_t).
\]

The current smoke-scale configuration uses 30-second clips at 4 FPS. The generator also supports negative clips with no pest, negative frames inside positive clips, shard-friendly clip indexing via \texttt{start\_clip}, curated model directories together with exclude lists, and visibility filtering so that tiny or nearly invisible positives are not mislabeled.

\subsection{Label Format}
Bounding boxes are exported in normalized center-width-height form. For a pixel-space box
\[
(x_{\min}, y_{\min}, x_{\max}, y_{\max}),
\]
we define
\[
x_c=\frac{x_{\min}+x_{\max}}{2}, \qquad
y_c=\frac{y_{\min}+y_{\max}}{2}, \qquad
w=x_{\max}-x_{\min}, \qquad
h=y_{\max}-y_{\min}.
\]
If the image size is $W \times H$, then the normalized box is
\[
\tilde{b}
=
\left(
\frac{x_c}{W},
\frac{y_c}{H},
\frac{w}{W},
\frac{h}{H}
\right)\in[0,1]^4.
\]
Each annotation therefore has the form
\[
y=(c,\tilde{b}),
\]
where $c \in \{\text{rat}, \text{mouse}, \text{cockroach}\}$.

\subsection{Video-to-Detection Reuse}
The current detector stack consumes an image-detection dataset rather than a temporal model input. We therefore flatten clip folders into:
\begin{itemize}[leftmargin=1.5em]
    \item \texttt{images/},
    \item \texttt{labels/},
    \item \texttt{manifest.csv}.
\end{itemize}
This allows reuse of the same splitting, training, and evaluation code on video-derived frames.

\subsection{Detectors}
We implemented DETR as the initial transformer-based detector \cite{carion2020detr}. DETR predicts a fixed set of slots
\[
\hat{y}_i=(\hat{p}_i,\hat{b}_i), \qquad i=1,\dots,Q,
\]
where $\hat{p}_i$ is a class distribution over the pest classes plus a no-object class and $\hat{b}_i \in [0,1]^4$ is a normalized box. Training uses Hungarian matching to align predictions and ground-truth objects.

We also implemented a torchvision Faster R-CNN baseline \cite{ren2015fasterrcnn}. This became the practical local baseline after diagnosis because DETR exhibited confidence and ranking collapse on the current synthetic video-frame split, while Faster R-CNN trained cleanly and separated positive from negative frames much more reliably. We stabilized Faster R-CNN further with a \texttt{positive\_anchor} batching strategy, which ensures that each mini-batch contains at least one positive frame and avoids all-negative mini-batches that can cause non-finite losses in heavily negative datasets.

\subsection{Training Protocol}

The DETR experiments in this repository were used primarily as smoke tests and diagnostic runs rather than as the main benchmark. For the stable local baseline, we therefore adopt a Faster R-CNN detector using the \texttt{fasterrcnn\_mobilenet\_v3\_large\_320\_fpn} architecture initialized with pretrained torchvision weights. The model is trained for 3 epochs with a batch size of 2 and a learning rate of $5 \times 10^{-5}$. To improve optimization stability, we apply gradient clipping with a maximum norm of 5.0.

Because the current synthetic video-frame dataset contains a substantial proportion of negative frames, training additionally uses positive-anchor batching to ensure that each mini-batch contains at least one positive example. This design helps avoid unstable all-negative batches and contributed to the reliability of the Faster R-CNN baseline in our local experiments. For implementation stability on Windows, data loading is performed with zero worker subprocesses.
\subsection{Evaluation Protocol}
The current evaluation pipeline is thresholded rather than mAP-based. A predicted labeled box $(\hat{c}, \hat{b})$ is counted as a true positive when:
\begin{enumerate}[leftmargin=1.5em]
    \item the predicted class matches the ground-truth class,
    \item the confidence exceeds a chosen threshold $\tau_{\mathrm{conf}}$,
    \item the box overlap satisfies
    \[
    \operatorname{IoU}(\hat{b}, b)\ge \tau_{\mathrm{IoU}}.
    \]
\end{enumerate}

We compute
\[
\operatorname{Precision}=\frac{TP}{TP+FP},
\qquad
\operatorname{Recall}=\frac{TP}{TP+FN},
\qquad
\operatorname{TDR}=\operatorname{Recall}.
\]

The current false positive metric is frame-level on negative frames:
\[
\operatorname{FPR}_{\mathrm{frame}}
=
\frac{\#\{\text{negative frames with at least one prediction}\}}
{\#\{\text{negative frames}\}}.
\]
The main reported operating points are confidence thresholds 0.5 and 0.2 with IoU threshold 0.5.

This is the strongest local benchmark currently supported by the repository.

\subsection{DETR Diagnosis}
The DETR diagnosis is informative. Its held-out v4 test recall is zero at thresholds 0.5 and 0.2, but this is not because it produces no scores at all. Instead, the diagnostics show that the top scores on both positive and negative frames cluster around 0.025, so thresholds of 0.05 and above suppress all predictions. Even top-$k$ truncation does not recover a clean operating point. When the threshold is lowered to 0.01, recall rises, but the frame false positive rate reaches 1.0. This is best interpreted as a collapse in confidence and ranking.

\subsection{Faster R-CNN Diagnosis}
The Faster R-CNN diagnostics show healthy score separation. On v5 test frames, the positive top-score quantiles are high, while the top scores on negative frames are exactly 0.0. As a result, thresholds of 0.5 and 0.2 both remain clean, and positive-anchor batching eliminates skipped training and validation batches.

\subsection{Engineering Status}
The repository now contains a complete local pipeline that includes smoke-scale 30-second clip generation, per-frame labels, flattened video-frame datasets, held-out train/validation/test splits, detector training and evaluation scripts, qualitative overlays, assembled MP4 demo clips, and report-ready comparison and summary figures.


\section{Reproducibility Notes}
\subsection{Core Artifacts}

\subsection{What a Reproducer Needs}
To reproduce the current local results, a reader needs the repository code, the \texttt{pest-synth} environment defined in \texttt{environment.yml}, Blender, the curated pest model assets, kitchen background images, and the documented generation, split, training, and evaluation steps. The raw binary assets and generated datasets are intentionally treated as local artifacts rather than normal git-tracked files, so a complete reproducibility package should include either direct dataset links or a separately shared asset pack and dataset pack.

\section{Discussion}
\subsection{Why the Current Results Matter}
The current results matter for several reasons. They show that the synthetic clip generator can produce coherent labeled data, that the flattened frame pipeline can train a detector reproducibly, and that negative examples can be incorporated without destabilizing the current Faster R-CNN baseline. They also show that model architecture choice matters strongly in this regime.

\subsection{Limitations}
The current system still has several important limitations. First, the strongest baseline is not the transformer-based model originally hoped for. Second, the results are purely local synthetic held-out results and do not prove real-world or instructor-test generalization. Third, the generator is still smoke-scale rather than assignment-scale. Fourth, the repository still does not adapt scene layout from a single user-provided kitchen image.

\subsection{Expected Failure Modes Beyond the Current Split}
Even though v5 performs perfectly on the local synthetic held-out split, several failure modes are still likely in harder settings. These include domain shift from rendered kitchen backgrounds to real camera footage, missed detections under stronger occlusion or clutter, sensitivity to unseen pest shapes or asset textures, failure under layout conditions not represented in the current background pool, and degraded performance when clip duration, motion, or scene complexity scale up.

\section{Future Work}
The next development steps are to scale the generator from smoke-scale 30-second runs to assignment-scale 30--60 second batches, add scene adaptation from a single user-provided kitchen image or justify a baseline approximation, validate the current baseline on external or instructor-provided test videos, revisit transformer-based detectors after the larger video pipeline is in place, expand model diversity, hard negatives, and realism to reduce the synthetic-to-real domain gap, and study whether synthetic pretraining plus limited real fine-tuning improves robustness.


\section{Conclusion}
This project develops a reproducible synthetic-data pipeline for pest detection in kitchen environments. The repository now goes beyond static image generation: it supports smoke-scale 30-second clip generation, per-frame label export, video-to-detection flattening, detector training, diagnostics, demo video assembly, and report-ready artifacts.

Empirically, the strongest current local baseline is Faster R-CNN with positive-anchor batching on \texttt{video\_frame\_smoke\_v5}. On the local held-out synthetic test split, this model achieves recall 1.0, precision 1.0, and frame-level false positive rate 0.0 at confidence thresholds 0.5 and 0.2. DETR, while implemented successfully, currently suffers from confidence and ranking collapse on the analogous smoke-scale video-frame split and is therefore not the recommended local baseline at this stage.

The main contribution of the current project stage is therefore twofold: a working synthetic video-frame generation and labeling pipeline, and a stable local detector baseline that demonstrates the pipeline can support meaningful training and evaluation. The major remaining gap is not basic engineering feasibility. It is closing the distance from local synthetic smoke-scale success to assignment-scale video generation, single-image scene adaptation, and external validation on held-out test videos.
